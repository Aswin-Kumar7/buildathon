# Sentinel data-foundation audit

Date: 2026-08-27

## Result

```text
storefront context → Razorpay checkout → signed webhook inbox → canonical events
→ features → rules/change detection → binary abuse model → arbitration → policy
→ one correlated incident → related attempts → merchant action → audit
```

An attempt is one resolved `razorpayPaymentId` and its lifecycle events. An incident is a
correlated activity episode keyed by entity and activity start. Multiple lifecycle events remain
one attempt, and multiple suspicious attempts can remain one incident.

## Findings and fixes

- Replay now drains all rows, runs replay-scoped detection before returning, reports incident
  counts, and marks every replay row explicitly.
- The live Attempts API now defaults to `source=razorpay`; replay requires an explicit source.
  Unresolved checkouts use the same source boundary.
- Incident detail resolves related canonical orders and attempts by entity pseudonym and activity
  time range. Counts are derived from returned attempts, never fabricated from observations.
- Incident deduplication remains backend-owned: canonicalisation, detector clustering, duplicate-view
  removal, database incident key/upsert, and same-activity checks prevent duplicate episodes.
- Overview attempt counts use resolved live attempts. Risk level and trend use detected live
  incident scores. Top reasons group live incident hypotheses from arbitration.

## Source of truth

`canonical_events` owns Razorpay outcomes; `checkout_sessions` owns merchant-observed context;
`incidents` owns correlated risk episodes; containments, transitions and `audit_log` own actions.
Replay is retained for explicit simulation but is excluded by backend queries from live views.

## ML audit

The deployed binary risk model was not changed or retrained. Its versioned feature vector matches
the served detector path and its opinion/contributions are recorded. Metrics remain held-out
synthetic-corpus metrics; no real merchant-labelled dataset exists here, so no real-world recall or
precision claim is made.

## Acceptance state

- Fresh live state returns zero attempts/incidents/containments and neutral/empty risk views.
- One genuine storefront payment produces one live resolved attempt and no incident unless warranted.
- Lifecycle events do not become separate incidents.
- Suspicious replay attempts use the real pipeline and can produce one correlated replay incident.
- Replay does not contaminate live Overview, Attempts, risk trend or reasons.
- Recommendations, actions, statuses and audit entries remain separate backend records.
- Policy candidates have a durable draft → submit → admin approve → admin publish lifecycle;
  publishing activates only a validated approved document and records an audit entry.

## External deployment inputs

Azure must register `https://<container-domain>/api/webhooks/razorpay` in Razorpay Test Mode and
provide the matching `RAZORPAY_WEBHOOK_SECRET`, durable `DATABASE_URL`, `PSEUDONYM_KEY_V1`, and
`PAYLOAD_KEY_V1`. Real merchant labels and external dashboard registration cannot be generated by
repository code.
