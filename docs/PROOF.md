# Proof

What Sentinel measurably does, how the corpus was built, which checks would catch us lying, and what
is still wrong.

Two source files are regenerated by CI on every build and are the authority for everything here:

- [`METRICS.md`](../METRICS.md) — the detector's scenario results
- [`ml/models/incident/artifacts/metrics.json`](../ml/models/incident/artifacts/metrics.json) — the
  model's held-out evaluation, with [`model_card.md`](../ml/models/incident/artifacts/model_card.md)
  beside it

Figures below are copied from those files. If the two ever disagree, the generated files win and
`pnpm check:metrics` will already have failed the build.

## 1 · Two measurements, and the difference between them

This is the most misread part of the project, so it goes first.

**The model alone.** A held-out grouped split of 1,325 entities.

**The system.** Rules and arbitration running the full pipeline over 11 scenario families,
1,105 entities judged.

They measure different things and produce different numbers. Both are real. The gap between them is
the leash from [DECISIONS](DECISIONS.md#3--the-model-recommends-it-never-acts), stated
numerically.

---

## 2 · The model

Gradient-boosted ensemble, 200 trees, temperature-scaled. Grouped split, so no entity appears in both
train and test.

|           |     Value | 95% CI         |
| :-------- | --------: | :------------- |
| PR-AUC    | **0.991** | [0.986, 0.995] |
| Recall    | **0.979** | [0.961, 0.993] |
| Precision | **0.875** | [0.836, 0.909] |
| ROC-AUC   |     0.997 |                |
| Brier     |     0.017 |                |

A no-skill baseline scores **0.211** on this corpus.

Everything above derives from one confusion matrix over **1,325 entities — 280 attack, 1,045
benign**:

|                    | flagged | not flagged |                 |
| :----------------- | ------: | ----------: | :-------------- |
| **attack** (280)   |     274 |           6 | recall 97.9%    |
| **benign** (1,045) |      39 |       1,006 | 3.7% flagged    |

> **Read the denominators.** 97.9% is measured over attacks; 3.7% over benign entities. They are not
> complements. The figure that pairs with 97.9% recall is the **2.1%** of attacks missed.

The operating point is not chosen by eye. The block threshold (0.07) minimises expected cost given
declared costs: a missed attack at 500,000 paise, a false positive at 80,000. Review rate is 2.9%
against a 3% cap.

## 3 · The system

From [`METRICS.md`](../METRICS.md), regenerated by `pnpm metrics` and gated by `pnpm check:metrics`.
Every entity of every kind is arbitrated independently, so an entity appearing under two kinds is
counted twice — that inflates the denominators and is the honest way round, because it counts every
opportunity the detector had to be wrong.

| Non-attack scenario | Entities | Contained | Sent to review |
| :------------------ | -------: | --------: | -------------: |
| `normal_traffic`    |      144 |         0 |              0 |
| `customer_error`    |      119 |         0 |              0 |
| `gateway_outage`    |      177 |         0 |              0 |
| `retry_storm`       |        6 |         0 |              0 |
| `flash_sale`        |      496 |         0 |              0 |

**0 false positives across 1,105 entities judged.** Every attack family recognised — four contained
outright, two escalated to a person. Nothing benign or operational was ever acted against.

`gateway_outage` is the one to read closely: it produces the highest raw failure count of any
non-attack family and the detector still opens nothing, because the failures are attributed to the
gateway and spread across sessions rather than concentrated. That is the signature of an outage, and
naming it is what stops the model's volume-driven suspicion from winning.

### Where the two measurements diverge

The model flags 39 benign entities; the system contains none. Those 39 concentrate in three places:

| Origin                              | Flagged by model |
| :---------------------------------- | ---------------: |
| `aggressive_dunning`                |          20 / 31 |
| `retry_storm`                       |          10 / 33 |
| `masked_loud_in_dunning_background` |           9 / 165 |

All three are billers retrying their own failures. Arbitration recognises them as `retry_storm` and
refuses to let the model escalate. **This is the whole argument for the leash**, and it is why the
model's false-positive rate is published rather than buried: it is the number the governance is for.

## 4 · Three checks that can fail in public

Each runs in CI and fails the build.

**Leakage canary.** The strongest single feature alone (`log_attempts`) reaches PR-AUC 0.554; the
model reaches 0.991 — a lift of **0.437**. The corpus is not separable by any one column, so the
score comes from the combination rather than a giveaway.

**Grouped-split check, with its sign published.** A careless row-wise split scores 0.907 with 474
entities appearing on both sides. The honest grouped split scores 0.991 with zero overlap. The
grouped score is the **higher** of the two — the opposite of the usual leakage story, and worth
stating plainly: the row-wise split does not inflate the score here, it fragments each scenario
across the boundary and makes the task look harder than it is. Neither number is flattering by
accident; both are regenerated every run.

**Model ladder.** The served model is re-proved against alternatives on every run:

| Model                     |  PR-AUC | Brier | Served |
| :------------------------ | ------: | ----: | :----- |
| Gradient boosting + temp. |   0.991 | 0.017 | **✓**  |
| Random forest             |   0.988 | 0.020 |        |
| Logistic regression       |   0.940 | 0.044 |        |

It must also win across five stability seeds, and does, by a mean margin of 0.058. If it ever stopped
winning, CI would say so.

**Cross-language parity** is asserted below **1e-8**, by a test that reimplements the tree walker
independently rather than calling the trained model — so a disagreement means one of them is wrong
about the artifact.

## 5 · Data provenance

- **The labels are synthetic.** Every row is an entity from a seeded scenario this project authored;
  the label is the scenario's declared ground truth, not a confirmed chargeback. `registry.json`
  records `data_source: synthetic-cardtesting` and `real_label_count: 0`, and `make eval` writes that
  disclaimer into every artifact.
- **The specifications were committed before the detector was tuned against them.** The corpus is
  generated in-process from `@sentinel/corpus` at a fixed seed, and `make eval` is deterministic: two
  runs produce byte-identical `metrics.json`.
- **The corpus is deliberately not trivially separable.** It carries boundary cases built to overlap:
  a tester reusing a small card pool (dunning-shaped), a benign batch walking many cards
  (enumeration-shaped), and attacks hidden inside ordinary traffic, a flash sale and an outage.
- **The path to real labels exists in the schema.** `incidents` carries a label column for an
  analyst's verdict or a chargeback that lands later. Until a merchant's own confirmed incidents
  populate it, every number here describes behaviour against a specification, not against the
  field.

## 7 · What is still wrong

The section that makes the rest of this document worth reading.

### Detection

- **Card reuse: 37 of 42.** A tester who reuses a small pool of cards looks like a biller retrying,
  and the overlap is genuine rather than a tuning failure.
- **Loud attack hidden in dunning: 10 of 11.** Same cause, from the other direction.
- **39 benign entities flagged by the model.** Contained by arbitration today. If a merchant's real
  dunning traffic differs in shape from the corpus, that margin is where it will show.

### Evidence

- **The labels are synthetic.** Stated above, and repeated here because it is the single largest
  limitation on every number in this file.
- **Latency figures are stale.** [`performance/loadtest.json`](performance/loadtest.json) was
  measured against the previously served linear model and has not been re-run against the ensemble.

### Console

Findings from a full audit, triaged and not yet fixed:

- **Three definitions of "Active" for incidents.** The Overview counts `open + under_review`; the
  Incidents filter means `open + contained`; the table labels `open` as "Active" and `contained` as
  "Contained". Selecting "Active" therefore shows rows labelled two different ways.
- **Two attempt counts on one incident screen.** The Overview tile shows the frozen feature-vector
  count; the tab label recomputes from related orders with a 100-order cap. They disagree.
- **`band` is a confidence band rendered as a risk band.** In `score.ts` it measures the width of the
  abstention interval, so a confident zero and a confident one are both `high`. Four places in the
  console render it as though it meant risk.
- **The Health page pools replay traffic** into tiles whose captions say it does not. Only
  `eventsStored` and `replayedEvents` are source-split.
- **The Attempts "Today" filter is UTC-aligned** while the client builds a local calendar date, so in
  IST it drops the first 5½ hours.

### Code quality

- **`SimulationPanel` has cyclomatic complexity 46** against a cap of 15. It is not hidden by the
  [JSX rule scope](DECISIONS.md#12--two-lint-rules-off-for-the-console); it is recorded here as
  outstanding.

## 8 · Reproducing all of it

```bash
pnpm check                     # every CI gate
pnpm metrics                   # regenerate METRICS.md from the corpus
cd ml/models/incident
make eval                      # retrain, re-evaluate, rewrite every artifact
make test                      # split integrity, parity, reproducibility
make check-metrics             # fail if anything drifted
```

`make eval` is deterministic from a fixed seed. If your `metrics.json` differs from the committed
one, that is a finding, and we would like to hear about it.
